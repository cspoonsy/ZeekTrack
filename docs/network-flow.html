Flows on the wire (captured by the SPAN)

# Source → Destination Protocol Purpose Zeek log
1 web-modbus → controller-pi:5020 Modbus/TCP Continuous poll to render UI (~every 500 ms) modbus.log · conn.log
2 controller-pi:5020 → web-modbus Modbus/TCP Poll responses — register values modbus.log
3a attacker → controller-pi:5020 Modbus/TCP Drive the train directly (HR writes) · throw the switch via M10 (coil 1/2 writes) modbus.log
3b attacker → web-pi:1883 MQTT Direct pub/sub on choochoo/# — snoop schema, publish switch/sw1/cmd/throw without going through the outstation (V-series) mqtt_connect · mqtt_publish · mqtt_subscribe
4 controller-pi → web-pi:1883 MQTT Switch controller pub/sub · M10 SwitchMirror · retained discovery / LWT mqtt_connect · mqtt_publish · mqtt_subscribe
5 web-modbus ↔ mosquitto (same host) MQTT Switch panel state — both containers on same Docker host not on the wire · inside Docker bridge
6a operator → web-pi:8000 HTTP Page load, static assets, REST commands (/api/motor, /api/switch/throw) http.log
6b operator → web-pi:8000 HTTP → WebSocket 101 upgrade, then long-lived JSON state (throttle, switch position, direction, liveness) http.log (101 only) · conn.log (long duration)

Three things to notice

Flow 5 is invisible to Zeek

Both containers share the Docker host, so this MQTT chatter never crosses a physical NIC — it stays inside Docker's bridge. Flow 4 (the cross-device MQTT) is the interesting stuff and is on the wire.

WebSocket masquerades as HTTP

Flow 6b's handshake is GET /ws/state + 101 Switching Protocols — lands in http.log. Everything after is opaque frames on a long-lived TCP session. Detection rules that only read http.log will miss operator activity entirely.

BLE is off-network by design

BuWizz and Circuit Cube speak BLE directly to the controller Pi. Zeek can't see radio, so anything past the Pi is invisible. Every teachable attack surface lives on the LAN side (Modbus + MQTT).
